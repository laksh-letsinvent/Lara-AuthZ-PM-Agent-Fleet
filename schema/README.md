# Schema

The consolidated SpiceDB schema, generated by concatenating all `domains/*/schema-fragment.zed` files. SpiceDB only sees this consolidated file at runtime — the fragments exist for SME ownership and review.

## Status

Not yet generated in v1. Until other domains populate their fragments, the consolidated schema is effectively `domains/accounts/schema-fragment.zed`. When a second domain populates, the consolidation step becomes meaningful.

## How consolidation will work

Mechanical concatenation in a deterministic order:

1. `domains/accounts/schema-fragment.zed` (first — exports shared definitions and caveats)
2. `domains/payments/schema-fragment.zed`
3. `domains/cards/schema-fragment.zed`
4. `domains/communications/schema-fragment.zed`
5. `domains/customer-mgmt/schema-fragment.zed`

Output: `schema/consolidated.zed`. Validated by SpiceDB's own schema linter before being considered usable.

## Who owns this step

Borderline eng. For v1 solo, manual concatenation when needed. When the framework ports to work, the Tech Lead builds a tiny script that runs on any fragment change. It is **not** worth being its own agent — the step is deterministic and mechanical, not judgment-driven.

## Discipline

- `consolidated.zed` is **never hand-edited**. Edit the fragments.
- Cross-domain references in fragments must reference exported names from `domains/accounts/schema-fragment.zed` (the anchor). The Accounts SME is informed of new external dependencies whenever another fragment references theirs.
- The consolidated file is checked in (when generated) so the prototype and any test harness can pin to a known schema state without re-running consolidation.
