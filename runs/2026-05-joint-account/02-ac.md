  A joint account holder can initiate an account closure request; the schema permits
  the can_close permission for any holder on a non-blocked account.
subject:
  relation: account#holder
action:
  permission: can_close
resource:
  type: account
  state: not blocked
expected: allow
negative_case: |
  A delegate cannot initiate account closure (can_close = holder only). (AC-A-020)
anchors:
  - BCOBS
notes: |
  The schema gates closure at the holder level. Dual-consent (both holders must confirm)
  is an application-layer workflow, not a schema constraint. The schema does not enforce
  the 14-day async consent window — it only confirms "this subject is a holder on a
  non-blocked account." The workflow gate is an application-layer requirement.
  Regulatory basis: BCOBS good practice requires both holders' consent before executing
  closure of a joint account given its irreversibility.

## Group 4: Bereavement State

```yaml
id: AC-A-013
use_case: UC-A-001
domain: accounts
status: approved
statement: |
  When a joint account enters bereavement state (blocked@flag:bereavement), all write
  operations are denied for all subjects, including the surviving holder.
subject:
  relation: any (holder, delegate_view_pay, ops_agent)
action:
  permission: can_transact, can_freeze, can_manage_payees, can_cancel_scheduled, can_close, can_delegate
resource:
  type: account
  state: blocked@flag:bereavement
expected: deny
anchors:
  - FCA Consumer Duty (PRIN 2A)
  - BCOBS
notes: |
  is_blocked = blocked (any flag value). bereavement is a valid flag value.
  All write-gated permissions use (... - is_blocked). This AC asserts that bereavement
  is treated as a blocking state identical in effect to frozen or suspended.
  The surviving holder's read access is preserved separately (AC-A-014).
source_run: runs/2026-05-joint-account
```

```yaml
id: AC-A-015
use_case: UC-A-001
domain: accounts
status: approved
statement: |
  After survivorship is confirmed — the deceased holder's account#holder relation is removed
  and the bereavement flag is cleared — the surviving holder regains full write access on the account.
subject:
  relation: account#holder
  notes: sole surviving holder, post-survivorship confirmation
action:
  permission: can_transact, can_freeze, can_delegate, can_manage_payees
resource:
  type: account
  state: not blocked (bereavement flag removed, deceased holder relation deleted)
expected: allow
anchors:
  - BCOBS
  - FCA Consumer Duty (PRIN 2A)
notes: |
  This is a state-transition scenario. The sequence is:
  1. Account blocked with flag:bereavement (all writes denied)
  2. Deceased holder's account#holder relation deleted via DeleteRelationships
  3. Blocked flag deleted via DeleteRelationships
  4. Surviving holder is now sole holder — full write access restored
  Consistency posture: CHECK must use at_least_as_fresh(survivorshipZedToken) where
  survivorshipZedToken is the ZedToken returned by the final DeleteRelationships call.
source_run: runs/2026-05-joint-account
```
